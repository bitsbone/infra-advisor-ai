The Datadog SDK shortens the path from supported Python frameworks to useful Agent Observability traces. InfraAdvisor relies on automatic integrations for library operations and adds explicit spans only where application-specific orchestration would otherwise be invisible.

**Source of truth:** `services/agent-api/src/`

## The boundary to understand

| Application behavior | How it becomes observable |
|---|---|
| LangChain or OpenAI model request | Automatically instrumented by `ddtrace` |
| LangGraph node execution | Automatically instrumented by the LangGraph integration |
| LangChain and MCP tool calls | Automatically instrumented as nested tool operations |
| Query workflow, routing, history load, source extraction | Explicit `LLMObs.workflow`, `LLMObs.agent`, or `LLMObs.task` spans |
| Product-specific domain, source count, or tool choice | Explicit annotations and bounded tags |

Automatic instrumentation describes supported libraries. Explicit instrumentation describes what those operations mean to InfraAdvisor.

## Bootstrap before instrumented libraries load

`ddtrace.auto` must be imported before LangChain, OpenAI, MCP, Redis, or other patched libraries:

```python
# services/agent-api/src/agent.py
import ddtrace.auto

from ddtrace.llmobs import LLMObs
from langchain_openai import AzureChatOpenAI
from langgraph.prebuilt import create_react_agent
```

The service enables Agent Observability during startup. A telemetry configuration failure is logged without taking the API down; observability should reveal application failure, not create it.

```python
def enable_llm_obs() -> None:
    LLMObs.enable(
        ml_app=os.environ.get("DD_LLMOBS_ML_APP", "infra-advisor-ai"),
        agentless_enabled=os.environ.get("DD_LLMOBS_AGENTLESS_ENABLED", "false").lower() == "true",
    )
```

## Model the orchestration once

The request workflow adds meaning around auto-instrumented children:

```python
with LLMObs.workflow("query-processing") as workflow:
    LLMObs.annotate(span=workflow, input_data=query)
    tools = await mcp_client.get_tools()  # opens an MCP session — keep it inside the workflow

    with LLMObs.task("load-history") as history_span:
        history = await load_history(session_id)
        LLMObs.annotate(span=history_span, tags={"history.turns": len(history)})

    with LLMObs.agent("router") as router_span:
        decision = await route(query, history)
        LLMObs.annotate(span=router_span, tags={"query.domain": decision.specialist})

    with LLMObs.agent(f"specialist-{decision.specialist}"):
        result = await react_agent.ainvoke(...)

    LLMObs.annotate(span=workflow, output_data=answer)
```

Do not wrap an automatically instrumented model or tool call in another manual `LLMObs.llm()` or `LLMObs.tool()` span. That produces duplicate operations without adding meaning.

Annotate while the context manager is active. An annotation made after the `with` block targets a span that has already closed.

## Give every root span readable input and output

The Agent Observability trace list shows each trace's **root** span input and output, not the content of the chat span deep inside it. Tags alone leave the row reading "No content" even when the nested OpenAI span holds the full prompt and answer. InfraAdvisor sets `input_data` (the effective user query) and `output_data` (the final answer) on the `query-processing` workflow and the specialist agent span, and sets the chosen specialist as the router's output.

The ddtrace MCP integration traces every MCP client session as its own `workflow` span, and that span's input is the session's `read_stream`/`write_stream` objects. Any `get_tools()` call made outside an explicit workflow becomes a root trace whose only content is `{"read_stream": "MemoryObjectReceiveStream(...)"}`. Keep MCP session work inside the request workflow. Standalone operations such as the startup probe, `GET /tools`, and the sandbox `POST /tools/{name}` each get their own named workflow (`mcp-startup-probe`, `list-mcp-tools`, `sandbox-tool-call`) with meaningful input and output.

## Connect the steps in the execution graph

Nesting tells the execution graph which spans belong to a step, not how data moves between steps. The graph draws an arrow between two sibling spans only when one carries a span link to the other, with `from`/`to` attributes naming the direction ([Datadog span links](https://docs.datadoghq.com/llm_observability/instrument/otel_instrumentation/)). Without links, `load-history`, `router`, and the specialist render as unconnected boxes. ddtrace's LangGraph integration links its own nodes, which is why the specialist's `agent → tools → agent` loop already shows arrows.

ddtrace has no public span-link API for manual spans, so `observability/llm_obs.py` wraps the private `LLMObs.annotate(_linked_spans=...)` parameter in one helper, `link_from(span, *upstream)`, which records output → input links. InfraAdvisor links the data that actually flows: the router's decision and the loaded history feed the specialist, and the specialist's messages feed `extract-sources`. `tests/test_llmobs_span_links.py` runs LLMObs for real and fails if a ddtrace upgrade changes the private parameter.

The root stays a `workflow` span. Datadog defines a workflow as a predetermined sequence of operations and an agent as a series of decisions made by an autonomous agent ([span kinds](https://docs.datadoghq.com/llm_observability/terms/)). `query-processing` always runs the same steps; the decisions happen inside the router and specialist, which are `agent` spans.

## Keep capture intentional

Automatic integrations can capture prompts, completions, model metadata, token counts, and tool inputs or outputs. That is useful for debugging only when the service's data policy allows it.

InfraAdvisor is a demo environment that relies on Datadog Sensitive Data Scanner to redact at intake. Agent-api spans therefore carry query and answer content. InfraAdvisor still disables Agent Observability payload capture on the provider-adapter MCP deployment. That service retains ordinary APM timing and bounded metrics without copying external provider bodies into Agent Observability. Changing this boundary requires an explicit privacy review and updated tests.

## Diagnose the missing boundary

| Symptom | Likely boundary |
|---|---|
| No model spans | `ddtrace.auto` loaded too late or the integration/version is unsupported |
| Library spans exist but no workflow | Explicit orchestration wrapper did not run |
| Duplicate model or tool spans | An auto-instrumented call was also wrapped manually |
| Tags missing | Annotation ran after the span closed |
| Trace list shows "No content" | Root span was annotated with tags only — add `input_data`/`output_data` |
| Root input is `{"read_stream": ...}` | An MCP session (`get_tools()`, tool call) ran outside any workflow span |
| Agentless export fails | `DD_API_KEY` or direct-ingestion configuration is missing |
