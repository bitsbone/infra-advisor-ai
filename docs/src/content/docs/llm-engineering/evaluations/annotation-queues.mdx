Annotation queues create a structured human-review workflow around production traces. Their value is not merely adding labels: reviewers can expose failure modes that automated evaluators do not yet understand and create trusted examples for later experiments. No InfraAdvisor annotation queue is configured in repository code; this page describes a future review workflow.

## Start with one decision

A queue should answer a specific question, such as:

- Did the response cite enough evidence for an infrastructure recommendation?
- Did the selected MCP tools match the user's intent?
- Does a low groundedness score represent a real failure or a judge mistake?

Avoid a large, generic “review quality” form. Every additional label increases reviewer effort and makes definitions harder to apply consistently.

## Proposed InfraAdvisor workflow

1. Select a narrow cohort in Trace Explorer, such as failed deterministic evaluations or negative user feedback.
2. Create a queue with one primary label and an optional reasoning field.
3. Have two domain-aware reviewers independently label the first shared sample.
4. Discuss disagreements and rewrite the label definition.
5. Review subsequent traces in small batches.
6. Promote representative, high-confidence examples into a regression dataset.

For current navigation, queue limits, automatic routing, and export behavior, follow Datadog's [Annotation Queues documentation](https://docs.datadoghq.com/llm_observability/evaluations/annotation_queues/).

## What good output looks like

The result is more than a queue completion percentage. Capture:

- a definition another reviewer can apply;
- examples of clear pass, clear fail, and borderline behavior;
- recurring failure categories;
- disagreements between humans and automated judges;
- a small set of durable regression cases.

<Aside type="tip">
Optimize for label consistency, not review volume. If reviewers interpret a label differently, more annotations only produce a larger unreliable dataset.
</Aside>
