Use this path when a quality rule belongs in source control and needs application context such as called tools, raw tool results, extracted sources, or the classified query domain.

## 1. Choose the cheapest reliable evaluator

Prefer a deterministic rule when the expected behavior is unambiguous. It is cheaper, faster, and easier to debug than an LLM judge. Use a judge for semantic questions such as relevance or groundedness, then calibrate its scores against human review.

An evaluator must return one of the metric types accepted by `EvalResult`: `boolean`, `score`, or `categorical`.

## 2. Implement `IResponseEvaluator`

The existing business-development ordering evaluator is the smallest useful model:

```csharp
public sealed class MyEvaluator : IResponseEvaluator
{
    public string Label => "my_quality_rule";

    public Task<EvalResult> EvaluateAsync(EvalInput input, CancellationToken ct)
    {
        var passed = /* evaluate input.Query, input.Answer, or input.ToolsCalled */;
        return Task.FromResult(new EvalResult(
            "boolean",
            passed,
            passed ? "Rule satisfied" : "Explain what evidence was missing"));
    }
}
```

Keep the label stable: dashboards and monitors will depend on it. Make reasoning specific enough to diagnose a failure without copying unnecessary prompt or tool content.

## 3. Register it with dependency injection

Register the implementation alongside the existing `IResponseEvaluator` services in `Program.cs`:

```csharp
builder.Services.AddSingleton<IResponseEvaluator, MyEvaluator>();
```

`AgentService` receives all registrations, applies one `EVAL_SAMPLE_RATE` decision to the response, and schedules each selected evaluator in the background.

## 4. Test behavior and non-applicable inputs

Test at least three cases:

- the rule passes;
- the rule fails with useful reasoning;
- the rule does not apply to the input.

For rules that do not apply, follow the existing evaluator convention deliberately. Some current deterministic evaluators return a passing result with `Rule N/A` reasoning. If non-applicable cases should be excluded from pass-rate calculations, evolve the shared result contract rather than silently inventing a new convention in one evaluator.

## 5. Verify the delivery path

<ObservationChecklist>

- Run the .NET test suite.
- Start the service with valid Datadog configuration and a temporary sample rate of `1.0`.
- Send a request that exercises the new rule.
- Check `/eval/status` for the registered label and submission result.
- Confirm the evaluation is joined to the intended agent span in Datadog.
- Check logs for evaluator exceptions or API rejection details.

</ObservationChecklist>

## When to add Python parity

Do not copy this page's C# into an imagined Python abstraction. The Python backend currently has feedback submission and a standalone faithfulness task, not a pluggable response-evaluator pipeline. Implement the missing dispatcher and tests first, then document the resulting contract from the code.

<Aside type="caution">
Never await optional evaluators on the `/query` response path. A judge timeout or Datadog intake error should affect evaluation coverage, not the user's answer.
</Aside>
