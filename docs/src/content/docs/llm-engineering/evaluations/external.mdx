External evaluations let application code calculate a result and attach it to an existing Agent Observability span. Use them for rules that need domain knowledge, tool results, or source-controlled logic.

## The join is the essential idea

The application finishes an agent span, evaluates the response asynchronously, and submits a boolean, score, or category with the span's trace and span IDs. Datadog uses those IDs to place the result on the original span.

If the IDs identify the wrong span—or disappear when work moves into the background—the score cannot appear where expected. Treat span identity as part of the evaluator contract.

## Current implementation

| Capability | .NET backend | Python backend |
|---|---|---|
| User feedback submission | Implemented | Implemented |
| Sampled evaluator dispatcher | Implemented | Not implemented |
| Deterministic evaluator interface | Implemented | Not implemented |
| Relevance and groundedness judges | Implemented | Faithfulness task only |
| Datadog evaluation API client | Implemented | SDK handles feedback submission |
| In-app pipeline diagnostics | `GET /eval/status` | Not implemented |

The backends intentionally teach different approaches; they should not be described as equivalent.

## .NET: a pluggable evaluator pipeline

`IResponseEvaluator` receives the query, answer, called tools, captured tool results, sources, and query domain. Five registered implementations currently run on the same sample decision:

- `citation_present` checks for extracted sources or recognizable infrastructure identifiers.
- `bd_tool_ordering` checks the order of two business-development tools when both are used.
- `tool_routing_accuracy` checks conservative query-to-tool rules.
- `meai_relevance` uses Microsoft.Extensions.AI.Evaluation to judge whether the answer addresses the question.
- `meai_groundedness` judges the answer against captured tool results.

Deterministic checks are fast and explainable. The two M.E.AI evaluators each add a judge-model call, so sampling controls their cost.

`DatadogEvalsClient` submits every result through one boundary and records recent outcomes for `/eval/status`. This gives the application a place to distinguish evaluator failures, missing configuration, and rejected submissions.

## Python: a narrower experiment

The Python backend currently demonstrates two separate mechanisms:

- `LLMObs.submit_evaluation()` attaches categorical user feedback to a known span.
- A background `faithfulness-eval` task calls a judge model, annotates its own task span with `eval.faithfulness_score`, and emits a DogStatsD gauge.

That faithfulness task does **not** use the .NET `IResponseEvaluator` contract and does not submit a joined external evaluation metric. Adding Python parity would require a dispatcher, evaluator modules, tests, and a reliable span-context handoff.

## Failure boundaries

Evaluators run after the user-facing work and must not turn a scoring failure into a failed answer. That keeps latency and availability independent, but fire-and-forget work can be lost during shutdown. A durable queue is the next design step if evaluation delivery becomes operationally important.

<ObservationChecklist title="Verify one .NET evaluation">

- Temporarily choose a sample rate that guarantees the test request is selected.
- Send a query that clearly matches one deterministic rule.
- Confirm `/eval/status` lists the evaluator and a successful submission.
- Open the agent span in Datadog and confirm the label, value, and reasoning are attached to that span.
- Restore the normal sample rate.

</ObservationChecklist>

<Aside type="caution">
Captured tool results may contain sensitive source data. The .NET pipeline truncates individual results, but truncation is not redaction. Review the capture policy before enabling broad evaluation coverage.
</Aside>
