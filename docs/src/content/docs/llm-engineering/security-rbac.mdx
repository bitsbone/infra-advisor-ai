Agent traces can contain prompts, responses, tool arguments, tool results, and retrieved context. Protecting that data requires several independent controls. No scanner or role compensates for sending content that was never needed.

## Apply controls in order

1. **Minimize capture in the application.** Prefer bounded metadata when raw content is not required for the learning goal.
2. **Redact or classify at ingestion.** Use Datadog's current sensitive-data capabilities for content that must be captured.
3. **Restrict data access.** Limit who can query Agent Observability data and which ML applications they can read.
4. **Govern derived copies.** Apply equivalent controls to exports, notebooks, dashboards, monitors, and correlated APM data.
5. **Review regularly.** Product permissions and capture behavior evolve independently of repository code.

## What InfraAdvisor controls in code

The provider-adapter MCP deployment disables Agent Observability payload capture and HTTP query-string tagging because provider responses and authenticated URLs can contain sensitive values. Multimodal spans use bounded metadata rather than filenames, media URLs, transcripts, or generated descriptions. Structured chat artifacts normalize and allowlist client-visible fields instead of forwarding raw provider responses.

These decisions make the default educational environment safer while preserving timing, status, modality, tool, domain, and correlation signals.

## What must be configured in Datadog

Datadog currently exposes `llm_observability_read` and `llm_observability_write` permissions. Default managed roles include these permissions according to their privilege level, so “access is opt-in” is only true after an administrator creates and assigns an appropriate custom-role model.

Restricted Datasets can constrain Agent Observability event data by `ml_app`. Datadog notes that some related resource metadata and correlated telemetry may not share the same restriction. Review [Agent Observability data access control](https://docs.datadoghq.com/account_management/rbac/data_access/) and the current [permission reference](https://docs.datadoghq.com/account_management/rbac/permissions/) before relying on a role design.

## Review checklist

- [ ] Document which spans capture input, output, tool data, attachments, and session identifiers.
- [ ] Verify the capture behavior of both Python and .NET with sentinel test data.
- [ ] Scope read access to the ML applications each role needs.
- [ ] Apply matching controls to APM and other correlated products where data is duplicated.
- [ ] Keep export application keys outside request-serving workloads.
- [ ] Define retention and deletion for exported or annotated copies.
- [ ] Recheck permissions and product support after Datadog configuration changes.

<Aside type="caution">
Redaction after ingestion is not a reason to emit secrets. Tool outputs should return the minimum data the model needs, and credentials should remain references to a secret system rather than model-visible values.
</Aside>
