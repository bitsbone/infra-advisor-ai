One query is enough to establish the minimum useful loop: application work becomes an Agent Observability trace, and the trace explains which agent, model, and tools participated.

This quickstart uses the project's existing instrumentation. To understand how it is wired, continue to the [Datadog SDK and OpenTelemetry comparison](./instrumentation/paths/).

## 1. Confirm the telemetry path

<Tabs syncKey="lang">
  <TabItem label="Python — Datadog SDK">

The Python service loads `ddtrace.auto` before its instrumented libraries and enables Agent Observability through `LLMObs.enable()`. The essential runtime settings are:

```yaml
DD_LLMOBS_ENABLED: "true"
DD_LLMOBS_ML_APP: "infra-advisor-ai"
DD_LLMOBS_AGENTLESS_ENABLED: "false"
DD_SERVICE: "infra-advisor-agent-api"
DD_AGENT_HOST: "datadog-agent.datadog.svc.cluster.local"
```

With agentless mode disabled, the Datadog Agent forwards both application and Agent Observability telemetry.

  </TabItem>
  <TabItem label=".NET — OpenTelemetry">

The .NET service registers its GenAI activity sources with OpenTelemetry and exports OTLP through the Datadog Agent collector:

```yaml
OTEL_SERVICE_NAME: "infra-advisor-agent-api-dotnet"
OTEL_EXPORTER_OTLP_ENDPOINT: "http://datadog-agent.datadog.svc.cluster.local:4318"
OTEL_EXPORTER_OTLP_PROTOCOL: "http/protobuf"
DD_ENV: "production"
DD_VERSION: "1.0.0"
```

The collector translates supported GenAI attributes into the Agent Observability span model.

  </TabItem>
</Tabs>

## 2. Send a tool-using query

Select either backend in the InfraAdvisor UI and ask:

> Which Texas bridges are in poor condition?

This query is useful because it should require agent reasoning, an LLM call, and at least one MCP tool. If you are exercising the API directly, send the same authenticated `/query` request used by the UI.

## 3. Locate the trace

In Datadog, open **Agent Observability → Traces** and filter by the backend service:

- Python: `service:infra-advisor-agent-api`
- .NET: `service:infra-advisor-agent-api-dotnet`

Open the newest trace. Ingestion may take a short time; use the response trace ID when available instead of relying only on recency.

<ObservationChecklist>
  <ul>
    <li>The root operation represents the complete request rather than one model call.</li>
    <li>Agent, LLM, and tool work appear as nested operations.</li>
    <li>The model, provider, duration, token counts, and error state are available where emitted.</li>
    <li>The tool span identifies the infrastructure lookup selected by the agent.</li>
    <li>The trace can continue into related application APM work.</li>
  </ul>
</ObservationChecklist>

## If the trace is incomplete

| Symptom | Check first |
|---|---|
| No trace | Runtime variables, Agent/collector reachability, and service startup logs |
| Model call missing | SDK import order on Python; registered activity sources on .NET |
| Tool call missing | MCP instrumentation and cross-service `traceparent` propagation |
| Trace split into separate trees | Multiple tracers or lost W3C context |
| Prompt content intentionally absent | Sensitive-data capture settings and the service's telemetry policy |

Use the language-specific [Python](./instrumentation/python/) or [.NET](./instrumentation/dotnet/) troubleshooting section once you know which boundary failed.
