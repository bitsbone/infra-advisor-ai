InfraAdvisor produces many of the inputs needed for ongoing operations, but this repository does not currently define production Automation Rules. The patterns below are recommendations to implement after their underlying signals are verified.

## Review before automating

A useful weekly review asks:

1. Did request volume, errors, or latency change by backend or domain?
2. Did evaluation scores drift for a model or prompt version?
3. Did cost per successful request change because of longer prompts, retries, or additional tool calls?
4. Did one tool or provider become the dominant latency source?
5. Is human annotation keeping pace with the cases selected for review?

This review separates a product change from a telemetry gap. A missing metric or evaluation should not silently become an operational conclusion.

## Design monitors around decisions

| Decision | Signal | Guardrail |
|---|---|---|
| Investigate a quality regression | Evaluation score by prompt/model/backend | Require enough samples before alerting |
| Investigate runaway agent behavior | Tool calls or cost per trace | Exclude approved long-running workflows |
| Investigate provider degradation | Tool/provider latency and error rate | Alert on sustained change, not one request |
| Escalate unsafe output | Safety evaluation or AI Guard result | Preserve a human-review path |

## Add automation in stages

1. **Notify:** send context to a review channel without changing runtime behavior.
2. **Classify:** tag or route suspect traces into an annotation queue.
3. **Recommend:** generate a proposed rollback, feature-flag, or sampling action for approval.
4. **Act:** automate only a reversible response with a tested recovery path.

Avoid disabling services, changing prompts, or throttling production from a single noisy evaluation. LLM-judge results and sentiment signals are probabilistic and need calibration.

## Interpret cost carefully

Model cost may include agent calls, retries, summarization, and evaluator judge calls. Compare cost with successful outcomes rather than optimizing the smallest number in isolation.

Useful breakdowns include backend, query domain, model, prompt version, and tool choice. Do not add high-cardinality user or conversation identifiers to cost metrics.

<Aside type="caution">
Sampling external evaluations reduces evaluator spend but also changes the evidence available for automation. Record the sampling policy and require an adequate sample before comparing periods.
</Aside>
