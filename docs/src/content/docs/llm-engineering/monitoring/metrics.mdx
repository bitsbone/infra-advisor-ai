Traces retain the details of one request. Metrics answer aggregate questions cheaply over time. Emit a custom metric only when the aggregation is valuable and the same signal is not already available from Agent Observability or APM.

## Start with the question

| Question | Best signal |
|---|---|
| How many model spans failed? | Built-in Agent Observability or APM metric |
| How are tokens, duration, and estimated cost trending? | Agent Observability operational metrics |
| Which product domains receive the most completed conversations? | Custom counter |
| Which tools does the application actually invoke? | Custom counter or span-derived analytics |
| What feedback are users submitting? | Custom counter plus per-trace evaluation |
| Was this particular response grounded? | Evaluation attached to the trace, not a metric alone |

Avoid emitting custom copies of latency, error, token, or cost fields that Datadog already derives from spans.

## Current InfraAdvisor coverage

The two backends are not yet symmetrical:

- **.NET** emits `infra_advisor.conversation.completed`, `infra_advisor.tool.invoked`, `infra_advisor.feedback.submitted`, `infra_advisor.mcp.reconnect`, and a faithfulness histogram through an OpenTelemetry meter.
- **Python** currently emits the faithfulness score through DogStatsD. Conversation, tool, feedback, and reconnect counter parity remains open work.

The partial status is intentional. Dashboards must not imply cross-backend comparisons until the same metric contract exists on both sides.

## Keep dimensions bounded

Useful dimensions have small, controlled value sets:

- `query.domain`
- `tool.name`
- `rating`
- `backend`
- `reason`

Do not tag metrics with user IDs, conversation IDs, trace IDs, prompts, URLs, or arbitrary error messages. Those values create high cardinality, may expose sensitive content, and belong in traces or logs when permitted.

## Compose frustration instead of inventing it

“Frustrated user” is an interpretation, not an event the application can observe directly. Build the interpretation from independent evidence such as negative feedback, sentiment evaluation, repeated retries, and session behavior. Keeping the inputs separate makes the rule explainable when signals disagree.

<Aside type="caution">
A metric name in code does not prove the complete pipeline works. Verify that the meter is registered, the exporter or DogStatsD client can reach the Agent, the metric appears with expected tags, and dashboards distinguish backends with different coverage.
</Aside>
