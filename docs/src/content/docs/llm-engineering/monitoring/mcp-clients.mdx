An agent trace is incomplete if it ends at “call tool.” The useful debugging path continues through the MCP client, the server handling the tool, and the downstream provider request.

## The trace you are trying to preserve

```text
agent decision
└── execute tool                 Agent Observability: tool
    └── MCP client request       protocol operation
        └── POST /mcp            APM: agent API → MCP server
            └── tools/call       server-side MCP operation
                └── provider     HTTP, database, or search work
```

W3C `traceparent` is the continuity mechanism. Both services must instrument the MCP library, and the transport must propagate the active context.

## Instrument both ends

<Tabs syncKey="lang">
  <TabItem label="Python — Datadog SDK">

With `ddtrace.auto` loaded first, `ClientSession.call_tool()` is instrumented by the MCP integration. LangChain's MCP adapter may contribute an outer tool span while the MCP integration contributes the protocol-level child. The nesting is useful when each span represents a different boundary; do not add another manual tool span around both.

  </TabItem>
  <TabItem label=".NET — OpenTelemetry">

Register `Experimental.ModelContextProtocol` on the agent client and MCP server. Register `Experimental.Microsoft.Extensions.AI` on the agent service for the outer `execute_tool` operation:

```csharp
.WithTracing(tracing => tracing
    .AddAspNetCoreInstrumentation()
    .AddSource("Experimental.Microsoft.Extensions.AI")
    .AddSource("Experimental.ModelContextProtocol"))
```

The MCP SDK version must support trace-context propagation. An activity source registered on only one side leaves a visible gap even when the request succeeds.

  </TabItem>
</Tabs>

## Keep stateful sessions on one server replica

The MCP HTTP transport associates follow-up requests with an `Mcp-Session-Id`. A Kubernetes Service that sends the next request to another pod can produce a 400 or 404 even though tracing is configured correctly.

InfraAdvisor uses client-IP affinity:

```yaml
spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 3600
```

This is an application-availability requirement, not merely a tracing preference. Autoscaling and pod termination still need graceful handling so active sessions are not discarded.

<Aside type="caution">
Do not interpret every missing server span as a telemetry failure. A rejected or misrouted stateful MCP request may never reach the expected handler. Check the HTTP status and session routing first.
</Aside>

<ObservationChecklist title="Verify the service boundary">
  <ul>
    <li>The client tool decision and MCP protocol request share a trace ID.</li>
    <li>The server request is a child of the outbound client operation.</li>
    <li>The named `tools/call` operation identifies the selected tool.</li>
    <li>Provider HTTP, search, or database work appears beneath the server operation.</li>
    <li>Failures identify the boundary without recording raw provider bodies or credentials.</li>
  </ul>
</ObservationChecklist>

## Diagnose a broken chain

| Last visible operation | Likely boundary |
|---|---|
| Agent tool decision | MCP client instrumentation or source registration |
| Outbound HTTP request | Server propagation or server-side MCP instrumentation |
| Server request with 400/404 | Stateful session routed to the wrong replica |
| MCP tool operation | Provider client instrumentation or an intentionally suppressed provider boundary |

Continue to [Spans and traces](../spans-and-traces/) to query tool-related requests or [APM correlation](../apm-correlation/) to follow logs and database work.
