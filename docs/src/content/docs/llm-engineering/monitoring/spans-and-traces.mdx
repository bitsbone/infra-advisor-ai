A useful agent trace answers a causal question: how did this input become this answer? Read it from the request boundary inward rather than scanning every span equally.

<TraceViewer client:load spans={traceData.spans} />

## Read the trace in four passes

### 1. Establish the request boundary

Begin with the root operation. Confirm the service, environment, version, duration, error state, and conversation or session identifiers. If the browser initiated the request, verify that the RUM context continues into the backend trace.

### 2. Follow agent decisions

Find the router, planner, specialist, or agent operations. Ask:

- Which domain or specialist was selected?
- Did the agent use a tool when the question required current or external data?
- Did it repeat a model or tool call unexpectedly?
- Did a deterministic task become the latency bottleneck?

### 3. Inspect model and tool evidence

Model spans explain inference cost, tokens, latency, errors, and permitted input/output content. Tool spans explain which external capability the agent selected. Follow the tool call through MCP and into its provider operation when the trace crosses services.

### 4. Correlate supporting signals

Use APM, logs, database monitoring, RUM, and infrastructure metrics to explain what the Agent Observability spans alone cannot. A slow tool may actually be a slow provider request or database query.

## Query from a question

| Question | Starting query |
|---|---|
| Which production requests failed? | `env:production status:error` |
| Which model calls took more than five seconds? | `@meta.span.kind:llm duration:>5s` |
| Which traces used the bridge tool? | `@meta.tools_called:get_bridge_condition` |
| Which conversations have poor groundedness? | `@evaluations.meai_groundedness.value:<2` |
| Did a prompt version regress? | Filter to spans with `@meta.prompt.version:*`, then group by version and compare the same evaluation |

Use **trace** search when the root operation should match. Use **span** search when any nested operation may match. Group results by trace when investigating one logical request rather than one operation.

## Sessions and conversations are different

InfraAdvisor propagates the browser RUM session identifier so a trace can link to the user's replay. A conversation identifier groups turns in one chat. One browser session can contain several conversations, and one conversation can outlive a browser session.

Do not overload one identifier to represent both concepts. Use each for the question it answers:

- Session: what did this user experience in this browser visit?
- Conversation: what happened across this chat's turns?
- Trace: what work happened for this one request?

  <ul>

The goal is not a perfectly dense trace. Keep the smallest span model that answers operational and quality questions without duplicating the same operation at several instrumentation layers.
