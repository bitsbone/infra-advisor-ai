[Prompt tracking and management](/llm-engineering/monitoring/prompt-tracking/) cover *what* prompt a subagent ran and *where* it came from (the hardcoded fallback, or Datadog's Prompt Registry). This page covers *how a specific version gets chosen* — per environment, or per user — without a redeploy.

## Use the registry's own Feature Flag, not a custom one

An earlier version of this project avoided `__llmobs__.prompt.<prompt_id>` as an "undocumented internal convention" and built a separate, explicitly-named integer flag (`prompt-version.<prompt_id>`) instead. That reasoning didn't hold up: `__llmobs__.prompt.<prompt_id>` is **auto-provisioned by Datadog's Prompt Management product itself** — one Feature Flag per managed prompt, created the moment that prompt exists in the registry, no manual flag setup required — and Datadog's own [server-side evaluation metrics guide](https://docs.datadoghq.com/feature_flags/guide/server_flag_evaluation_metrics/) documents monitoring it directly. Maintaining a parallel custom flag added a second configuration surface for no real benefit. This project now evaluates the real flag in both backends and the custom one is gone.

The flag is **object-typed**, not a plain integer: reading it resolves `{prompt_id, version, template}` in one evaluation — the same shape the registry's REST fetch already returns — so a targeting hit can skip the HTTP round-trip entirely rather than just picking a version number to fetch afterward.

## How each backend evaluates the flag

**Python** (`services/agent-api/src/observability/prompts.py`): `fetch_prompt(prompt_id, fallback_template, *, targeting_key=None, attributes=None)` forwards straight to `LLMObs.get_prompt(prompt_id, fallback=fallback_template, targeting_key=targeting_key, **(attributes or {}))`. ddtrace's own `PromptManager._fetch_from_ff` (confirmed by reading the installed package directly) evaluates `__llmobs__.prompt.<prompt_id>` via the OpenFeature SDK whenever `DD_EXPERIMENTAL_FLAGGING_PROVIDER_ENABLED=true` and `DD_ENV` is set, falling through to the env-scoped `/resolve` HTTP path (which also receives `targeting_key`/`attributes`) on any non-hit.

**.NET** (`Services/PromptVersionFlags.cs`): `ResolveAsync(promptId, targetingKey, attributes)` evaluates the same flag as an object value via `FeatureClient.GetObjectValueAsync` (confirmed against the installed `OpenFeature` 2.3.0 package — the object is an `OpenFeature.Model.Structure` with `template`/`user_version`/`version` fields, the same shape `DatadogPromptManagementClient`'s REST parsing already expects). Returns `null` on any non-hit so `PromptHolder.RefreshAsync` falls through to the REST registry fetch, mirroring Python's fallthrough exactly.

Both fail open identically: any provider or evaluation error returns nothing (Python: `None` from `_fetch_from_ff`; .NET: `null` from `ResolveAsync`), and the existing registry/fallback-template behavior takes over — a Feature Flags outage must never block a prompt from resolving.

### Per-user targeting — the real reason this exists

The flag supports an `EvaluationContext` with a `targeting_key` and arbitrary `attributes` — evaluated fresh, per call, not cached against a fixed timer. Both backends pass the requesting user's id as `targeting_key`, and — when set — their [job_role demo attribute](#targeting-on-the-job_role-demo-attribute) as an `attributes` entry.

This is a meaningfully different resolution model from a pod-wide "refresh every 60s" cache:

- **Python** already calls `fetch_prompt()` fresh on every request — no caching tension at all.
- **.NET**'s `PromptHolder` still refreshes its **pod-wide default** on a ~60s timer (`PromptRefreshBackgroundService`) — unchanged, and still what every request uses when there's no per-user override. `SpecialistRegistry.GetWorkflowForRequestAsync` additionally evaluates the flag **fresh, per request**, with the calling user's `targeting_key`/`attributes`; only when that resolves to a version genuinely different from the cached default does it build a one-off `AIAgent`/workflow for just that turn (`AgentHolder.GetAgentForRequestAsync`). The common case — no per-user targeting rule configured, or this user has no override — costs nothing extra: it falls straight back to the cached workflow.

## Targeting on the job_role demo attribute

For demo purposes, every user has a `job_role` — one of five sample roles for the "public infrastructure engineering firm" narrative (`Civil Engineer`, `Water & Energy Analyst`, `Business Development Manager`, `Contracts Administrator`, `Program Director`), each mapped 1:1 onto an existing specialist domain. It's embedded directly in the JWT at login (`services/auth-api/src/auth.py`'s `create_token`) — both backends already validate JWTs locally with zero network calls back to auth-api, so reading `job_role` costs nothing extra. Editable per-user in the admin UI (`Chat → Admin → Users`, inline `NativeSelect`); a role change takes effect at that user's *next* login, the same staleness class as every other JWT claim.

To target on it: create a targeting rule on `__llmobs__.prompt.specialist-engineering` (for example) matching `job_role == "Civil Engineer"` → a specific version. Log in as a Civil Engineer and as a Program Director, ask both the same engineering question, and compare each turn's prompt-version badge (below) — only the Civil Engineer's turn should show the pinned version.

## Correlating to LLM spans needed no new plumbing

This is the part worth stating plainly: the resolved `{id, version, source}` flows into the *exact same* tagging path [prompt tracking](/llm-engineering/monitoring/prompt-tracking/) already documents — Python's `LLMObs.annotation_context(prompt=...)`, .NET's `prompt.version`/`_dd.ml_obs.prompt_tracking` activity tags (now resolved per-specialist via `gen_ai.agent.id`, since .NET has 6 prompts instead of 1 — see prompt tracking's tracking-pattern section). Nothing new was built for correlation; a flag-resolved version is just another value flowing through the same resolver that already fed those tags. In Datadog, a trace's `prompt.version` reads `ff-<version>` for a flag hit (or `registry-<version>`/a content hash for the unpinned path) so a dashboard, monitor, or evaluation query grouping by `prompt.version` sees a targeted rollout the same way it sees any other version change.

## Per-turn version visibility in the chat UI

Beyond the admin-only aggregate **Prompt versions** panel (`Chat → Admin → Prompt versions`, `GET /admin/prompts/status` / `GET /prompts/status` — one row per specialist's current pod-wide default, polled every 10s), each assistant message in the chat itself carries a small badge showing exactly which prompt answered *that turn* and its resolved version/source — the `done`/`DoneEvent` SSE event's `prompt_id`/`prompt_version`/`prompt_source` fields, sourced from whichever specialist the router actually handed off to. This is the fastest way to see a per-user targeting rule take effect live, without cross-referencing a trace.

## Setting a targeting rule

1. In Datadog's Feature Flags product, find `__llmobs__.prompt.<prompt_id>` (e.g. `__llmobs__.prompt.specialist-engineering`) — it already exists once that prompt is in the registry, no creation step needed.
2. Add a targeting rule matching on `targeting_key` (a specific user id) or an attribute like `job_role` → a specific registry version.
3. Confirm the change reached a running pod via the admin UI's **Prompt versions** panel for the pod-wide default, or — for a per-user rule — the affected user's next chat turn's version badge.

<ObservationChecklist title="Verify a targeting rule took effect">
  <ul>
    <li>The affected user's next turn shows the pinned version in the chat message's prompt-version badge.</li>
    <li>A fresh trace's <code>prompt.version</code> tag reads <code>ff-&lt;version&gt;</code>, matching the pinned version.</li>
    <li>A different user (or the same user before their next login, for a job_role-based rule) still sees the pod-wide default.</li>
    <li>Removing the targeting rule restores the previous default/fallback behavior without a redeploy.</li>
    <li>A Feature Flags outage (simulate by clearing <code>DD_APP_KEY</code>/<code>DD_APPLICATION_KEY</code>) still resolves a usable prompt — check for a warning log, not a failed request.</li>
  </ul>
</ObservationChecklist>
