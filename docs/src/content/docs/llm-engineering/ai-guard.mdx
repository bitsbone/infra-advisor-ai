AI Guard evaluates messages before an agent acts on them. InfraAdvisor places a pre-flight check at the start of each query so an explicit block occurs before domain classification, retrieval, model calls, or MCP tools.

This is a safety boundary, not an observability evaluation. Post-response quality scores explain behavior after it happened; a guard decides whether processing may continue.

## Same decision point, different clients

| Concern | Python | .NET |
|---|---|---|
| Client | `ddtrace.appsec.ai_guard` SDK | Project-owned HTTP client |
| Input checked | Raw user query | Raw user query |
| Block result | Abort exception becomes a blocked response | `DENY` or `ABORT` becomes a blocked response |
| Failure policy | Fail open | Fail open |
| Local diagnostics | Application logs | APM activity, logs, `/ai-guard/status` |

### Python SDK path

`observability/ai_guard.py` creates a Datadog AI Guard client only when `DD_AI_GUARD_ENABLED=true`. `check_query()` evaluates one user message with blocking enabled. An `AIGuardAbortError` returns a user-safe block reason; client errors are logged and processing continues.

The service also runs Datadog auto-instrumentation. Supported downstream model or framework integrations may add further checks, but the explicit pre-flight call is what guarantees a clean application response before the agent workflow starts.

### .NET HTTP path

`DatadogAiGuardClient` posts the same one-message transcript to the regional AI Guard evaluate endpoint. Both query modes call it before any agent work. Because the HTTP API does not produce native AI Guard traces, the service adds three local signals:

- a child `ai_guard.evaluate` APM activity with bounded decision metadata;
- a trace-correlated structured log;
- a recent-outcome buffer exposed by `GET /ai-guard/status`.

These signals prove that the application called the API; they do not make the request appear as an SDK-generated AI Guard trace.

## Understand the fail-open choice

Missing credentials, client initialization failure, transport errors, and malformed responses allow the query to continue. This preserves availability during an observability-provider failure, but it also means “service healthy” does not imply “guard active.” Monitor the enabled state and failed checks separately.

<ObservationChecklist title="Test both outcomes">

- Confirm the guard reports enabled before testing blocking behavior.
- Send an ordinary request and verify the agent workflow still runs.
- Send an approved test case that should be blocked and verify no retrieval, model, or tool work follows it.
- On .NET, confirm the status endpoint, APM activity, and log agree on the action.
- Simulate unavailable credentials in a non-production environment and verify the documented fail-open behavior.

</ObservationChecklist>

<Aside type="caution">
The current pre-flight sends raw user text to AI Guard. Treat the application and Datadog account configuration as part of the same data-processing boundary, and do not copy the text into custom span tags or logs.
</Aside>
