Parity means a user can complete the same job and an investigator can answer equivalent questions. It does not require identical code, trace names, or agent topology.

## Deliberate architecture differences

| Layer | .NET | Python |
|---|---|---|
| Web framework | ASP.NET Core | FastAPI |
| Agent | Microsoft Agent Framework single-agent path | LangGraph router plus specialists |
| Model abstraction | Microsoft.Extensions.AI | LangChain Azure OpenAI |
| MCP client | ModelContextProtocol.Client with cached holder | LangChain MCP adapter refreshed per request |
| AI telemetry | OpenTelemetry, Microsoft AI decorators, OTLP | `ddtrace.auto` plus explicit `LLMObs` spans |
| Hot memory | MAF session serialization in Redis | Project message serialization in Redis |

The memory formats are intentionally not interchangeable. Both derive a tenant-scoped key from authenticated identity so a raw client session or conversation ID is not the isolation boundary.

## User-visible coverage

| Capability | .NET | Python | Notes |
|---|---:|---:|---|
| Authenticated query and conversation history | ✓ | ✓ | Shared client contract, separate agent memory format |
| Non-streaming response | ✓ | ✓ | Answer, sources, steps, attachments, artifacts |
| SSE streaming and live tool steps | ✓ | ✓ | Same event family, different framework adapters |
| Curated and generated suggestions | ✓ | ✓ | Both have a seed pool and tool-grounded generation |
| Image and audio attachments | ✓ | ✓ | Same upload/reference validation contract |
| Procurement evidence artifacts | ✓ | ✓ | Same artifact schema, separate extractors |
| Tool catalog and normalized provider behavior | ✓ | ✓ | Keep language implementations contract-tested |

## Observability and operations

| Capability | .NET | Python | Interpretation |
|---|---:|---:|---|
| End-to-end agent and MCP traces | ✓ | ✓ | Trees differ by framework; investigate equivalent boundaries |
| Log and RUM-to-APM correlation | ✓ | ✓ | OpenTelemetry/Serilog versus ddtrace injection |
| PostgreSQL and DBM evidence | ✓ | ✓ | Attribute/collector path versus ddtrace propagation |
| Explicit AI Guard pre-flight | ✓ | ✓ | .NET HTTP client; Python Datadog SDK client |
| Downstream automatic AI Guard coverage | — | framework-dependent | Verify supported Python integrations at runtime |
| Prompt version | content hash | missing | .NET evaluator config can still use a separate env version |
| Response evaluator framework | five evaluators | missing | Largest quality-layer gap |
| User feedback submission | ✓ | ✓ | Both attach categorical feedback to a span |
| Faithfulness signal | histogram plus external groundedness judge | task annotation plus gauge | Not the same metric or delivery contract |
| Business counters | conversation, tool, feedback, reconnect | missing except faithfulness gauge | Dashboards must split by backend |
| Evaluation diagnostics endpoint | ✓ | missing | Python has no equivalent dispatcher to diagnose |
| MCP reconnect recovery | cached-client retry | fresh per-request client | Different lifecycle; do not copy the .NET holder without evidence |

## Current evaluator catalog

The .NET response pipeline registers three deterministic checks—citation presence, business-development tool order, and routing accuracy—and two Microsoft.Extensions.AI judges for relevance and groundedness. Python has a background faithfulness task and user-feedback submission, not equivalent evaluator modules.

See [External evaluations](/infra-advisor-ai/llm-engineering/evaluations/external/) for the exact contracts. Do not document hypothetical Python files before they exist.

## Prioritized gaps

1. **Standardize prompt identity.** Apply the same content-derived version algorithm to Python and to .NET evaluation tags without exporting templates or user content.
2. **Design Python evaluation delivery.** Decide how background work preserves target span identity, failure diagnostics, and shutdown behavior before porting individual checks.
3. **Add bounded business metrics.** Match names and dimension contracts only where the aggregate question is useful on both backends.
4. **Calibrate quality signals.** Define whether Python faithfulness and .NET groundedness are comparable; rename or separate them if they are not.

<Aside type="note">
Implementation symmetry is not automatically an improvement. Python's per-request MCP client avoids the stale cached-session failure that motivated the .NET reconnect holder, while the .NET evaluator abstraction provides capabilities Python genuinely lacks.
</Aside>
