InfraAdvisor has four distinct flows. Keeping them separate prevents common misconceptions—for example, Kafka is not on the interactive request path, and a faithfulness gauge is not automatically a span-joined external evaluation.

## Interactive query

<Mermaid code={`
sequenceDiagram
    actor Client
    participant Proxy
    participant Agent as Selected Agent API
    participant State as Redis / PostgreSQL
    participant Model as Azure OpenAI
    participant MCP as Matching MCP Server
    participant Source as External source

    Client->>Proxy: query or streaming query + auth
    Proxy->>Agent: route by backend prefix
    Agent->>Agent: validate attachment references
    Agent->>Agent: AI Guard pre-flight
    Agent->>State: load memory
    Agent->>Agent: classify and retrieve context
    Agent->>Model: route / reason
    Model->>MCP: select tool
    MCP->>Source: provider request
    Source-->>MCP: provider response
    MCP-->>Model: normalized tool result
    Model-->>Agent: answer
    Agent->>State: save memory and conversation
    Agent-->>Client: answer, sources, steps, artifacts, trace identity
`} />

Python models routing with explicit `LLMObs` agent spans around framework calls. .NET performs deterministic domain classification and uses Microsoft agent and OpenTelemetry operations. The resulting trees differ, but both should explain the selected path and evidence.

### Optional work after the answer

Python schedules a faithfulness model task, annotates its task span, and emits a gauge. .NET samples its registered response evaluators and submits their results against the completed agent span. These are different delivery contracts and can be lost if the process stops before fire-and-forget work completes.

## Synthetic Kafka loop

```text
Load Generator CronJob
  └─ produce infra.query.events
       └─ Python Agent API consumer
            ├─ run the ordinary agent path under a system tenant key
            └─ produce infra.eval.results
```

The result event includes the answer, sources, tools, latency, corpus type, and domain. Its `faithfulness_score` field is currently `null` because the Python faithfulness task completes independently. Data Streams Monitoring observes the Kafka path; it does not turn the result topic into a completed evaluation store.

## Ingestion and retrieval

```text
government source → Airflow fetch → private Blob snapshot
                                      │
                                      └─ transform / chunk / embed → Azure AI Search
```

Each source has its own schedule and transformation details. The shared invariant is that raw snapshots remain recoverable in private storage while the search index is a derived serving layer. See [Data pipeline](/infra-advisor-ai/data-pipeline/) for per-source behavior.

## Conversation and memory state

PostgreSQL stores durable conversation records. Redis stores a tenant-scoped hot-memory representation and model choice with a TTL. The agent derives its key from authenticated user identity plus conversation or session input; a raw client identifier is never the complete isolation boundary.

The suggestion pool is separate shared Redis state maintained by background work. It reduces page-load inference latency and does not belong to an individual conversation.

<ObservationChecklist title="Locate one datum at each stage">

- Identify where the user's text, attachment reference, and authenticated identity enter.
- Distinguish normalized MCP results from client-facing artifacts and assistant prose.
- Confirm which state is durable in PostgreSQL and which is replaceable in Redis.
- Locate the Kafka result and note that its faithfulness field is not populated by the asynchronous judge.
- Follow trace context across the agent-to-MCP boundary without expecting the ingestion pipeline in the same trace.

</ObservationChecklist>
