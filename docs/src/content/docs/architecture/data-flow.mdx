InfraAdvisor has four distinct flows. Keeping them separate prevents common misconceptions—for example, Kafka is not on the interactive request path, and a faithfulness gauge is not automatically a span-joined external evaluation.

<FlowExplorer client:visible title="Follow one datum across the system" flows={systemFlows} />

## Interpret the boundaries

The interactive flow is the only path that directly serves a user's answer. Python models routing with explicit `LLMObs` agent spans around framework calls; .NET performs deterministic domain classification and uses Microsoft agent and OpenTelemetry operations. Their resulting trees differ, but both should explain the selected path and evidence.

The Kafka loop is synthetic background work. Data Streams Monitoring observes its producer, topic, consumer, and result path; it does not turn the result topic into a durable evaluation system. The result event's `faithfulness_score` is currently `null` because the Python faithfulness task completes independently.

The ingestion pipeline is another lifecycle entirely. Raw snapshots remain recoverable in private storage while Azure AI Search is a derived serving layer. A request trace can show retrieval from that layer, but it should not be expected to contain the earlier ingestion pipeline run. See [Data pipeline](/infra-advisor-ai/data-pipeline/) for per-source behavior.

PostgreSQL and Redis also encode different promises. PostgreSQL owns durable conversation records. Redis owns replaceable tenant-scoped hot memory and model choice with a TTL. The suggestion pool is separate shared Redis state maintained by background work; it reduces page-load inference latency and does not belong to an individual conversation.

<ObservationChecklist id="architecture-data-lifecycles" title="Prove that the lifecycles stay separate" prompt="Use the explorer and one real trace. Check an item only when you can identify the concrete stage or signal.">

- Identify where the user's text, attachment reference, and authenticated identity enter.
- Distinguish normalized MCP results from client-facing artifacts and assistant prose.
- Confirm which state is durable in PostgreSQL and which is replaceable in Redis.
- Locate the Kafka result and note why its faithfulness field is not populated by the asynchronous judge.
- Follow trace context across the agent-to-MCP boundary without expecting the ingestion pipeline in the same trace.

</ObservationChecklist>
